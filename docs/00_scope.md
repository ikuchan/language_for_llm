# 目的とスコープ

## 目的

AI が使うプログラミング言語について、**理論として理解し、言語を作る**こと。

- 議論の出発点（2026-10-17）で、著者は目的を「単に勉強したいだけ」と選んだ
- 同日、著者はこの作業場を「言語を作る為のセッション」として開いた

理論を詰める段階か、実装に進む段階かは、著者が決める。どちらも閉じない。

## 扱うもの

- 自然言語と機械語の隔たりを、言語がどう埋められるか
- 人間が中身を読まない前提で、出力の正しさをどう確かめるか（検証）
- 抽象化（省略）の扱い：何を省いたかの宣言と、省略の下へ降りる道（降下の道）
- 概念の識別：一つの語が複数の概念を覆う自然言語を、言語の側でどう扱うか
- 粗い概念から細かい概念へ、機械語まで滑らかに精度を保つこと
- 非機能要件（メモリ安全、定数時間性など）が、段を下りても保たれること

## 扱わないもの（著者が外した）

| 外したもの | 理由・経緯 |
|---|---|
| 信用・制度・責任の所在の話（建築・医薬・監査・保険の類推） | 著者の指示「信用の話はスコープ外に」。技術の設計と切り離す |
| 個別の題材での実験（性質を別の AI に書かせる等） | 著者の判断「個別具体な実験で得るものはなさそう」。一般の知見が出なかった |
| 学習データの量を、Python を選ぶ理由にすること | 著者の指摘「卵と鶏の話」。理由として数えない |
| 構築手順から入ること（変換器を先に作る、等） | 議論の入口として、著者が却下した（実装に進むこと自体を閉じたわけではない） |

## 著者が示した前提（設計の拘束）

| 前提 | 内容 |
|---|---|
| 人間は何も読まない | 検査点は、コードの中ではなく入口（意図の確認）と出口（動作の観察）に移る |
| 概念は離散的な ID ではない | 一つの語が複数の概念を覆うのが普通。抽象化するほど覆う範囲は広がる。概念は「事例の集合」として持つ |
| 粗さは言語が扱う | 大きい概念のままテストを通せる場合と、小さくしないと通せない場合を、言語自体が扱う（実際にはもっと滑らか） |
| ハッシュ表による記号化 | 今回作るものに必要 |
| 型付き | 型付き言語のように、宣言しないと動かない強制力 |
| 機械語まで | 最終的にアセンブラ水準まで落とせる精細さを、滑らかに保つ |
| C は終点にしない | 未定義動作によるメモリ漏洩など、セキュリティの問題が起きる |
| 目指すもの（2026-10-18） | 著者の言葉（原文）：「一級の言語であることと、AIにとって使いやすい言語であることを目指してます。」「一級」の意味は、著者の答え（2026-10-18、原文）：「第一級です」。何を第一級（一級の値）として扱うかは、最初に「分布」を選んだ（2026-10-18）。範囲も第一級にし、目的は値にしない（著者が提案を了承、2026-10-18）。 |
