# 議論のまとめ

これまでの議論を、話題ごとに並べ直したもの。各項に、根拠の種類を付けた。

- **確認** … 検索や実機で確かめた
- **記憶** … 私（Claude）の知識によるもので、確かめていない
- **見立て** … 推測・解釈。根拠は弱い

## 1. 出発点：何を狙う言語か

「AI が書く言語」と言っても、目的が違えば設計が反対になる。最初に目的を4つに分けた。

| 目的 | 中身 | 見立て |
|---|---|---|
| トークン節約 | 記号で短くする。SimPy は Python と可逆に変換し、トークンを最大 34.7% 減らしたと報告されている | すでに研究がある。上限が低い（見立て） |
| **検証が組み込まれた言語** | コードと仕様・証明を一緒に書かせ、コンパイラが合否を出す | 出力を人が信用できないことが、いまの詰まりどころ（見立て）。伸びしろが最大。**推奨** |
| エージェント実行の言語 | ツール呼び出し・再試行・並列・チェックポイントを構文にする | 余地がある |
| 文法制約デコーディング前提 | 生成時の制約で、必ず文法的に正しくなる形に設計する | CangjieBench では精度と費用の釣り合いで最良。ただし止められるのは構文までで、意味は別（確認：要旨まで） |

**最大の敵は学習データの偏り。** 慣れない言語を渡されると、エージェントは Python で試作する方へ戻る（Wu らの調査。確認：要旨まで）。ただし著者は、学習データの量を Python が最適な理由とは認めない（[00_scope.md](00_scope.md)）。

AI への書きやすさについての、Ronacher の経験則（計測ではなく本人の経験と推論）：

| 設計 | AI にとって |
|---|---|
| インデントで構造を表す | トークンがかさみ、一部だけ直すのが苦手 |
| 閉じ括弧が何十個も並ぶ | 個数を数え間違える（将来のモデルが直すかもしれないと留保あり） |
| 型推論 | 式の型が見えず、読む側が言語サーバーに頼る。型を書くほうが曖昧さが減る |
| 例外 | AI は何でも捕まえてログに出し、回復が下手。型つきの結果値のほうが向く（本人も不確か） |
| マクロ | 人にも AI にも難しい。コードが安く書けるので必要性も下がった |
| 再エクスポートや別名 | 宣言と使用が離れ、import を間違える |
| 失敗の条件が複数 | 「全部通ったか」が1コマンドで分かる形を好む |

見立て：**AI に効くのは、文法の見た目より、ビルド・テスト・エラーの出し方という道具の側。**

## 2. 自然言語とアセンブラの隔たり

足りないのは「変換の力」より、**意図の確定**と**途中で確かめる足場**。変換そのものは今のモデルでもできてしまう。

| 隔たり | 自然言語の側 | アセンブラの側 | 埋めるのに要るもの |
|---|---|---|---|
| 曖昧さ | 「速く」「大きいほう」で通じる | 1命令ごとに意味が1つ | 仕様（境界値、失敗時の動き、型） |
| 抽象度 | 「一覧を並べ替える」 | レジスタ、メモリ番地、ジャンプ | データ構造と制御の語彙 |
| 環境の知識 | 暗黙に前提される | CPU、呼び出し規約、OS で結果が変わる | 実行環境の明示 |
| 正しさの確認 | 人が読んで納得する | 動かすまで誤りが見えない | 検証（テスト、型、証明） |
| 資源の制約 | 書かれない | 命令の選び方で速度とメモリが決まる | 最適化の方針 |

コンパイラの途中の層（構文木、中間表現、アセンブラ）は、人間が読むためだけにあるのではない。**各層で1種類の誤りだけを確かめられる**足場である（記憶）。自然言語から直接アセンブラへ飛ぶと、その足場が全部なくなる（見立て）。

Meta の LLM Compiler のように、中間表現やアセンブラを直接扱うモデルの研究はある（記憶、2024年。未再確認）。ただし「できること」と「出力が意図に合うと確かめられること」は別。

### Python が最適な理由

学習データを除くと、ほぼ無い（Python は動的型で曖昧さが多く、検証の足場が弱い）。ただし「Python である理由がない」ことと「間に何も要らない」ことは別で、中間の層が残る理由が3つある。

| 理由 | 中身 |
|---|---|
| 監査 | 出力が意図に合うかを、誰がどこで確かめるかが決まらなくなる |
| 意図の保存 | 型や不変条件は後の検証の手がかりで、機械語に落ちると消える |
| 検証済みの部品 | ライブラリは、検証され使われ続けた振る舞いの蓄積。作り直すと保証も作り直し |

これが要求するのは「検査できる形で意図を持つ層」であり、それが Python である必要も、人間向けの文法である必要もない（見立て）。

## 3. 人間が読まない場合：入口・出口・実行の枠

「人間は何も読まない」とすると、検査点は2か所に移る。コードの中ではなく、入口と出口。

| 検査点 | 要るもの |
|---|---|
| 入口 | AI が解釈した意図を、自然言語と具体例で人間に返す「解釈の確認書」。人間が読むのはコードではなく確認書 |
| 出口 | 独立した検証。AI 自身が書いたテストは同じ誤解を共有しやすい（見立て）ので、出所の違う検査が要る |
| 実行の枠 | 権限を絞った箱、取り消せる実行、全操作の記録。中身を読めなくても、できることの範囲は読める |

代償：中身の誤りに途中で気づく機会を失う。取り消せない操作（送金、本番データ削除など）では致命的。

## 4. 出口の検査（記憶）

核心：**作るより確かめるほうが易しい仕事を探す。** 土台は変換の検証（translation validation）：生成器を信用せず、出力のたびに小さく信用できる検査器で入力と照合する。

| 技法 | 中身 | 効く例 | 効かない例 |
|---|---|---|---|
| 性質検査 | 出力が満たすべき性質を、ランダム入力で何千回も試す | 並べ替え、往復変換 | 性質を言葉にできない仕様 |
| 差分検査 | 独立した実装と結果を比べる | 信用できる既存実装がある処理 | 比べる相手が無い |
| 変性検査 | 正解が不明でも、入力と出力の関係を確かめる | 正解が出せない計算 | 関係が見つからない処理 |
| ファジング | 壊れた入力を大量に投げる | 入力を受ける部分の安全性 | 答えの正しさ |
| 実行時の監視 | 不変条件を見張り、破れたら止める | 取り返しのつかない操作の手前 | 事前の保証 |
| 影の実行 | 本番と並べて走らせ、反映はしない | 置き換え前の確認 | 初めての処理 |

限界は2つ。

1. **オラクル問題**：正しい答えを誰が持つか。
2. **誤りが同じ向きに揃う**：独立に作った実装でも同じ間違いをする（Knight と Leveson、1986）。AI は同じ学習から来るので揃いやすい可能性がある（見立て）。

言語設計への含意：「AI が書く言語」の中身は書きやすさよりも**検査の書きやすさ**（性質を実装と並べて書ける、実行時監視が組み込み、取り消せる操作と取り消せない操作を型で区別、全操作の記録を再生できる）。

### オブジェクト指向・開発手法

価値が残るのは「人間に読みやすい」ためではなく**検査できる境界を作る**ためのもの：契約による設計、カプセル化・インターフェース、依存の注入（ポートとアダプタ）、アクターモデル、イベントソーシング、DDD の共通言語、BDD、規約優先のフレームワーク。価値が下がるのは、継承の階層、読みやすさのための設計パターン、DRY、人間の記憶に収める分割（記憶・見立て）。取るのは契約と境界で、状態を持つオブジェクトそのものではない。

## 5. 実機で確かめたこと（Dafny 4.11.0）

**確認：実際に検証にかけた。** `Max`（2変数）と `Withdraw`（残高）の例。

| 例 | 結果 |
|---|---|
| 正しい `Max` と `Withdraw`、残高100から30を引く呼び出し | 検証済み、誤りなし。呼び出し側の `assert` も証明された |
| `Max` の本体を `m := a;` だけにした版 | 拒否。事後条件が破れる位置まで出た |
| 残高100に130を引く呼び出し | 拒否。事前条件を証明できない、と呼んだ行を指した |
| `ensures m >= a && m >= b` だけで、本体が `+1000000` した値を返す版 | **通った**（性質が足りないと、おかしな実装も通る） |

別の AI に性質だけを書かせ、また別の AI に本体を書かせる小さな実験も行った（最大値と並べ替え）。2件では、性質は穴なく書かれ、本体は1回で通った。ただし定番の題材なので一般化できない。著者の判断で、個別実験はここで打ち切った。

性質を一部抜いた版の判定（自分の手で確認した結果）：

| 悪い実装 | 完全な性質 | 一部を抜いた性質 |
|---|---|---|
| 最大値：常に 1000000 を返す | 拒否 | **拒否**（残した「どの要素以上でもある」を、1000000 より大きい要素を持つ配列で破るため） |
| 並べ替え：長さ同じで 0 だけ並べる | 拒否 | **通過**（要素の集合が同じ、を抜くと通る） |

（注：会話中の報告では最大値の行を「通過」と書いていたが、実際は拒否だった。訂正済み。）

そこから分かる一般的な点：**検査を書く側の力が、そのまま上限になる。** 要求22（仕様の弱さの検出）に対応する。

## 6. 省略（抽象化）の扱い：宣言と降下の道

抽象化は**情報を捨てる圧縮**で、捨てたものが結果に効かない間だけ成り立つ。Spolsky の「漏れる抽象化の法則」が、ずっと見ずに済んだものが障害の時に突然効く現象を言い当てている（記憶）。

省略を使うときに手元に必要な3つ：

| 問い | 中身 |
|---|---|
| 何を捨てたか | 省略の**宣言** |
| いつまで効くか | **有効範囲** |
| 漏れたとき降りられるか | **降下の手段** |

省略は暗黙のまま行われやすく、そこが危うい。

### 宣言が強制される既存の機構（記憶。検索では未確認）

| 言語・機能 | 省略するもの | 強制のされ方 |
|---|---|---|
| Rust の `unsafe` | コンパイラの安全保証 | 書かないと危険な操作を呼べない |
| Haskell の `IO`、Koka の効果型 | 副作用が無いという保証 | 副作用が型に出る |
| Idris・Agda の穴（hole） | まだ書いていない部分 | 穴が残ると実行できない |
| Lean の `sorry` と `#print axioms` | 証明していない部分、公理 | 印が付き、機械が一覧する |
| SPARK の `SPARK_Mode` | 検証していない領域 | 宣言で区切る |
| 漸進的型付け（TypeScript の `any`、Typed Racket） | 型を決めていない部分 | `any` が宣言。Typed Racket は境界で実行時検査 |
| EnerJ、`Uncertain<T>` | 精度を落としてよい値 | 近似が型の印になる |

### 降下の道の既存の機構（記憶）

Lean・Coq の証明項／Typed Racket の blame／Lisp・Smalltalk の実行中の検査／rr などの記録再生／Datalog 系の出自（provenance）／Unison のハッシュによる定義の特定。

### 空いているところ（見立て）

- 宣言が強制されるものは、対象が限られる（安全保証、副作用、未完成のどれか）
- 「何を要約で捨てたか、どの範囲で効くか」を型で宣言するものは、EnerJ 以外に見当たらない
- 降下の道と省略の宣言をつないで「この結果はこの省略に頼っている」と追えるものは、Lean の公理の追跡が最も近い

### 書く量の問題

宣言を毎回書くと、同じ概念を示すトークンは減らない。そこで：

| 仕組み | 中身 |
|---|---|
| 定義に1回 | 省略は抽象を作る場所に書き、使う場所には書かない |
| 推論で伝える | 省略に依存する側へ、ツールが自動で広げる |
| 標準の省略は書かない | 既定から外れたときだけ書く |

**狙うのは、書くトークンの節約ではなく、読むトークンと確認の手間の節約**（見立て。測っていない）。ハッシュによる記号化は別の手段として組み合わせる。

## 7. 概念の識別

著者の要求：ハッシュ表による記号化に加え、**似た概念だが定義が異なる場合**と**似た概念を混ぜて使っている場合**を区別する仕組みが必須。

当初案：語 → 概念ID → 定義ハッシュ の3層。**著者が否定した**：一つの語が複数の概念を包含するのが普通で、抽象化されれば包含する範囲が大きくなるのも当然。離散的な ID で語を切る前提は外れていた。

### 言語学の文献（検索で存在を確認。要旨・紹介ページまで。本文は通読していない）

| 文献 | 要点 |
|---|---|
| Kilgarriff 1997 "I don't believe in word senses" | 語義は辞書が並べるような離散的なものではない |
| Kilgarriff 1992 Polysemy（博士論文） | 多義は自然な種類ではない |
| Navigli 2009 WSD Survey | 語義曖昧性解消の標準的総説 |
| OntoNotes（Palmer ら） | 注釈者の一致率が90%以上になるまで語義を統合する |
| Temerko ら CoNLL 2025 | 規則的な多義の拡張が、言語モデルの驚き度に人間らしい段階で表れる |
| Kugler 2025 | 語義を、文脈つき埋め込みのクラスタとして定義する |

記憶のみ：Pustejovsky の Generative Lexicon、Wierzbicka の NSM、Cruse の Lexical Semantics、Wüster の用語学と ISO 704（概念を特徴の組で定義する）。

### 現在の設計

概念を**事例の集合**として持つ（束をなす）。使う側はまず一番粗い概念のまま使う。

| 状況 | 動き |
|---|---|
| 粗い概念のままテストが通る | そのまま。細分化しない |
| 通らない | 失敗した事例を手がかりに、**その部分だけ**を下位の概念として切り出す |

例：「1か月後」を最初は「30日後」と同じ粗い概念で使う。「3/1 の1か月後」は通るが、「1/31 の1か月後」で失敗する。この事例から「月末をまたぐ加算」を下位概念として切り出す。他の呼び出しは粗いまま残る。

近い既存技術（記憶）：CEGAR、抽象解釈、漸進的型付け・漸進的検証、精緻化型（Liquid Types）、ステップワイズ精緻化（Wirth、Event-B）。

## 8. CEGAR がそのままでは足りない4か所（見立て）

CEGAR：粗い抽象で検査し、反例が出たら元のプログラムで本物かを確かめ、偽物なら抽象を細かくしてやり直す。

| # | 足りない点 | CEGAR | 今回 |
|---|---|---|---|
| 1 | 割る単位 | 名前のない述語を自動生成して捨てる | 名前のある概念を、人と AI が使い続ける。割った後、旧来の使用箇所が A・B・両方のどれを指すか決め直す必要があり、「両方を指す」中間状態が要る |
| 2 | 偽物か本物かの判定 | 元のプログラムで反例を再生すれば確定する | 元は有限個のテストと、書かれていない意図。落ちた理由は3択（粗い／バグ／テストか意図の誤り）で、機械的には決まらない |
| 3 | 通ったことの意味 | 抽象が過大近似なので、抽象で安全なら元でも安全 | テストは有限個を試すだけ。粗いまま通った概念は「未反証」であって検証済みではない。**細かさの軸と確からしさの軸を分ける** |
| 4 | 履歴 | 検査が終われば洗練の過程を捨てる | 履歴が資産。いつどのテストが落ちて何と何に割ったかを残す。割る前の粗い語は「A または B」として残し、古いコードがそのまま読める |

CEGAR に既にあるもの：遅延抽象化（Henzinger ら、2002。記憶）。細かさを場所ごとに変える。ただし述語が無限に増えると終わる保証がなく、止める基準は別に要る。

補う部品：使用箇所の再解決（中間状態）／落ちた理由の3択判定（最も細かい段で落ちるなら本物のバグ。残りは AI が仮説を出し人へ）／細かさと確からしさの2軸／割り方をテストとハッシュに紐づけて保存／予算で止める。

## 9. 型付きであることと、機械語まで精細さを保つこと

結論（見立て）：**両立する。** 型付き言語は、粗い概念から細かい概念への順序を、すでに持っている。

| 型の機能 | 概念の側から見ると |
|---|---|
| 部分型 | 細かい概念は粗い概念の部分集合 |
| 精緻化型 | 述語を足して、いくらでも細かくできる |
| 依存型 | 型に値を含められる。ビット幅や配列長まで書ける |
| ダウンキャスト | 証明するか、実行時に検査する（漸進的型付け） |

精細さを機械語まで保つ仕組みは、部品ごとには実在する（記憶）。

| 仕組み | どこまで届くか |
|---|---|
| 型保存コンパイル（TIL、GHC の Core） | 最適化の途中まで型を保つ |
| 型付きアセンブラ（TAL） | 機械語の段階でも型検査 |
| CompCert、CakeML | 各変換が意味を変えないことを証明したコンパイラ |
| seL4 | 抽象仕様から C、さらに機械語まで、精緻化の関係を連ねて証明 |
| Vale（F\* 上）、Bedrock | 検証付きのアセンブラを証明系の中で書く |
| 広域言語、B 法、Event-B | 抽象から実装までを、1つの言語の中で段階的に具体化 |

滑らかには届かない3つの壁：

1. 検査の費用が、精細さに応じて急に上がる（ループ不変条件などの補助の注釈が要る）
2. 機械そのものの意味（命令セットの挙動）を、どこかで形式的に決めておく必要がある
3. 粗い概念を機械語に落とすとき、決めること自体が省略になる（ビット幅、桁あふれの扱い）。これも宣言の対象

足りないのは、**精度を上げ下げしたとき、検査（証明）の費用が滑らかに増減する仕組み**（見立て）。

## 10. 非機能要件

**C を終点にしない。** CompCert は「C の意味を保つ」だけで、C のプログラムが安全であることは保証しない。未定義動作を含む C は、そのまま未定義動作として機械語になる。

安全な終点の候補：検証付き IR から機械語へ直接（CakeML、Vale と HACL\*）／アセンブラに近い検証済み言語（Jasmin）／所有権・領域の型（Rust、Cyclone）／ハードウェアが強制（CHERI）／実行環境が強制（WebAssembly）。いずれも記憶。

非機能性質は、段を下りたときの振る舞いで3種類に分かれる（記憶・見立て）。

| 種類 | 例 | 段を下りたとき | 扱い |
|---|---|---|---|
| 全実行についての安全性 | 範囲外を読まない、解放済みを使わない | 下の段の意味が曖昧でなければ保存される。未定義動作があると崩れる | 型で排除。下の段に未定義を作らない |
| ハイパー性質 | 比較時間が入力で変わらない、使った秘密が残らない | **普通の精緻化では保存されない**。最適化が「無駄な書き込み」として秘密の消去を消すことがある | 性質ごとに、各変換で別に確かめる |
| 量的性質 | 100ms 以内、メモリ 1MB 以内 | 段ごとに数字が変わる。粗い段では意味を持たない | 段ごとの費用モデル。粗い段は上限や「不明」 |

要求としての整理は [02_requirements.md](02_requirements.md) の 23-1〜23-9。並行処理・分散は今回の範囲に入れておらず、23-8（考えていない性質の宣言）で扱う。

## 11. Lean 4 から実行ファイルは作れるか

作れる。ただし **C を経由する**（記憶。検索では未確認）。コンパイラが中間表現から C を出力し、C コンパイラが機械語にする。`lake build` で実行ファイルまで作れる。

- 型と証明は実行ファイルに残らない
- コンパイラは検証されていない（CompCert のような「変換が意味を保つ証明」はない）
- ランタイムは C/C++ で、参照カウントによるメモリ管理がここにある。検証の外
- `partial`、`unsafe`、`@[extern]` は型で守られない部分を入れる。`sorry` と公理は `#print axioms` で追える

Lean より低い段まで検証をつなぐものとしては、F\*（Low\* から C へ、Vale からアセンブラへ）と CakeML がある。評価表では要求17を△、要求18を×にした。
